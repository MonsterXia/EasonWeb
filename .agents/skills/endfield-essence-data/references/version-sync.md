# 双计算器版本同步流程

用于用户明确要求新版本或全量同步的一次对话。这里编排公开资料查找、现有导入器、素材同步和验证；不是一个已经能够自动下载全部最新数据的脚本。不执行发布或后台监控。

## 同步清单

除非用户缩小范围，每一行都要检查并记录“更新／核对无变化／缺失”，不以只增加新武器作为完成。

| 范围 | 统一目录或使用处 | 核对内容 |
| --- | --- | --- |
| 干员 | `catalog.characters` | 全部已实装 ID、中英文名、稀有度、职业、属性、武器类型、官方头像来源 |
| 武器 | `catalog.weapons` | 全部已实装 ID、中英文名、稀有度、类型、图片；基质 `essence` 主／副／技能类型与技能专名；排序 `essenceOrder` |
| 地区 | `catalog.regions` | 全部已开放淤积点的主属性、副属性、技能池；删除、改名及旧池调整 |
| 养成数值 | 实体 `levels/promotions/equipment/skills/nodes` | 每级经验／货币、突破边界与材料、装备适配、技能及专精成本、能力／战斗／后勤天赋成本与前置分支 |
| 材料与折算 | `catalog.materials/experienceGroups` | 中英文名、材料 ID、低阶材料图标 ID／稀有度、输入输出经验值与等级段；所有消耗和折算引用必须可解析 |
| 枚举与显示 | `catalog.filters`、`src/i18n/games.ts`、`src/i18n/growth.ts` | 武器类型、职业、属性、地区／词条显示翻译；新增枚举的筛选、图标及排序也须能显示 |
| 素材 | `src/assets/skland/`、头像 URL、图标组件 | 武器、材料、技能、专精／天赋、后勤、能力、属性、职业、武器类型、稀有度和已有官方 UI 纹理；检查新增、替换和缺图，保持两计算器共用 |
| 证据与工具 | 数据和素材来源清单、导入器、说明和测试 | 固定来源、版本、日期、哈希、计数、解析器适配、预期结果；不复制另一套 catalog |

“全部素材”指两个计算器实际引用的资源。无需重取无变化图片，也不扩展到其他森空岛页面的整套素材；共享资源变化时检查受影响的调用方。

## 确定版本与来源

1. 检查 `git status --short`、当前统一目录、数据 `sources.json`、素材 `sources.json`、导入器和相关测试。记录基线的 ID 集合、实体数量、来源版本、现有缺图及关键计算结果，保留既有未提交改动。
2. 联网查官方版本公告和实际开放时间。区分国服／国际服、正式实装／预告／测试服；默认国服已实装内容。用户指定未来或尚无完整事实数据的版本时，明确可完成范围，不用旧表填充未知新数值。
3. 查所用上游的当前内容并固定具体提交／游戏表版本。旧 `sources.json` 中的 SHA 只用于基线，不能直接当作新版本来源。公告用于判断实装范围，完整词条、消耗表与素材还需逐项取源核对。
4. 下载到仓库外临时目录；只解析 JSON 或上游生成文件中的数据字面量，不运行上游应用。对每个采用的原始文件记录 SHA-256、固定 URL／提交、实际版本和核对日期。优先官方公开资料，缺失时使用已标明出处的事实表／素材镜像；不能把第三方一致性称作游戏内验证。

基质字段按 [data-sources.md](data-sources.md) 处理。养成与图片的具体来源见 [GROWTH.md](../../../../src/constant/game/hypergryph/endfield/GROWTH.md) 和 [资源说明](../../skland-frontend/references/assets.md)。当前可用路径仅作定位线索，新版本要核实结构：

- CEP `src/generated/data/planner.ts`、`src/generated/data/wiki/{characters,weapons}.ts`、逐干员 wiki JSON、`src/generated/data/wiki/enums.json`。
- CEP `src/generated/i18n/{characters,weapons,wikiData}/{zh-CN,en}.json`、`public/images/characters/sources.json`。
- 一图流武器／物品／能量淤积点数据及中文词条；CEP 武器、地区数据用于交叉核对。
- 游戏表 `CharGrowthTable`、`ItemTable`、`ExpItemDataMap`、`WeaponExpItemTable`，分别提供视觉／天赋映射、材料图标 ID 和经验值。
- 现有素材清单中固定的 CEP `public/images/{weapon,items,wiki/skills,wiki/logistics,panel-preview}`、官方静态模块与 CDN。

## 准备完整的新目录

按稳定 ID 比较新增、修改、删除，而不是按名称模糊连接。更名应更新同条记录；掉落池按集合比较，保留合理顺序。目录摘要遗漏旧实体不等于游戏删除，删除必须有实装证据。无实装证据的预载条目不进入可选列表。

先在临时副本准备已核对的实体身份、武器 `essence`、地区、材料、经验规则和枚举，再合并养成输出。保留原目录直至新目录完整；不要让占位的空成本、新增武器的 null 副属性或未核对的旧消耗进入正式结果。

### 现有导入器的限制与升级顺序

`scripts/import-endfield-growth.py` 当前会锁定 CEP 提交、CharGrowthTable 哈希、版本和日期；读取现有目录并保留基质、地区和折算信息；发现新武器 ID、删除 ID 或共享类型／稀有度变化会拒绝导入。因此直接运行旧命令既不会刷新全部数据，也不能完成新版本同步。

1. 取得并核对新来源后，在本次任务内更新导入器的固定提交、表哈希、版本／日期及必要的字段解析。检查 `result.version/updatedAt` 与写入 `sources.growth` 的值，不能遗漏脚本末尾的固定值。
2. 在临时目录副本中按新来源补齐新武器的稳定 ID、名称、类型、稀有度、已核对的 `essence` 和唯一 `essenceOrder`。同时更新地区与折算数据；导入器会原样保留这两部分，不能期待它自动刷新。
3. 对已实装 ID 集合与上游完整摘要不一致的情况，先定位预载／缺失条目，再适配导入范围；不要简单删掉 ID／版本检查。共享字段变化应由新来源解释后写入临时副本。
4. 在临时副本的仓库相对目录结构下运行导入器，再核对所有字段和引用。低阶材料元数据会从现有目录保留，因此新经验材料须先补完。命令的两个参数是已经固定并核对的本地来源：

   ```sh
   python3 scripts/import-endfield-growth.py /path/to/pinned-cep /path/to/CharGrowthTable.json
   ```

5. 同一输入重复导入应产生一致输出。导入适配、素材清单或固定来源的更新都属于用户已请求的同步工作，无需让用户逐次授权；若来源缺少关键数值，保留有效数据并明确未同步条目，不能用默认值凑齐。

## 同步图片与显示

- 沿用 `src/common/endfieldResources.ts`、共享头像和图标组件，不为基质复制一份武器图片。实体 ID 对应 `ef-growth-<id>`；材料图标按真实 `ItemTable.iconId` 映射，不能把 item ID 当图标 ID 猜 URL。
- 干员沿用官方 CDN 头像与文字回退；游戏原图保持色彩和比例。未知新图标先查事实映射；暂时缺图可保留文字回退，但须列为缺失，不能称素材齐全。
- 新增／替换本地资源须同时更新 `src/assets/skland/sources.json` 的固定来源、原始／输出哈希和已有语义字段。删除前检查两计算器及其他共享页面是否仍有引用。
- `scripts/sync-overview-assets.mjs` 与 `tests/overview-assets.test.js` 当前含固定 CEP SHA／资源路径白名单。新版本采用新来源时一起精确更新允许的固定来源；旧素材仍引用旧提交则保留其可用性。不能放开任意下载域或关掉哈希校验。
- `npm run overview-assets:sync` 只按已更新清单重取，不会发现新实体或自动生成清单。图片不必无差别重下，最终用离线 `npm run overview-assets:check` 验证。
- 检查新增类型／职业／属性对应的 SVG／徽章、筛选次序、文案和材料回退；只改 JSON 而无法从页面选择新内容不算完成。

## 更新来源证据

统一数据写入 `catalog.json`，来源写入同目录 `sources.json`：

- 根层保留基质核对日期、游戏版本、武器／地区计数、公告及 `sources[].revision/files`。
- `growth` 记录养成的实际版本、核对日期、固定提交和视觉表证据；`experience` 独立记录经验表版本和原始文件哈希。来源未变时保留实际旧版本并说明“经核对无变化”。
- `catalog` 的数量和 SHA-256 按最终文件实际字节计算。格式化后若字节改变，须重新计算哈希。`consolidatedAt` 是历史整合日期，`original*Sha256` 是整合前历史证据，均不当作本次更新日期或新文件校验值。
- 同步数据 README／GROWTH 说明、必要的 UI 版本提示与测试预期。区分资料核对日期、提交日期、表版本和游戏实装版本，不把它们混为一谈。

## 验证与完成条件

使用项目 Node.js 24，在最终工作区执行：

```sh
npm test
npm run overview-assets:check
npm run build
npm run test:e2e -- tests/e2e/endfield-growth.spec.ts tests/e2e/endfield-essence-selection.spec.ts --workers=4
git diff --check
```

更新测试的版本锁定与数量断言必须有已核对的新 ID 集合作依据。至少覆盖：

- 两计算器共用同一目录；ID 唯一；每把武器的基质字段、类型与配图均能解析；排序、材料引用、三组或新版本实际折算规则完整。
- 新／修改武器的可行与不可行地区、主副技同时匹配、定向覆盖与高亮一致；三星缺副属性的语义不变或有新规则依据。
- 全部实体的合法等级、突破、装备、技能／专精、天赋边界；修改过的数值用原始来源手算样例或独立求和验证，不能只比较导入输出自身。
- 未改动实体的计算结果保持一致；合法改动的差异可追溯。新增天赋链、折算取整、共用库存和已有本地历史恢复可用。等级上限／阶段等规则变动时同时适配算法和控件，不能仅扩大表。
- 桌面及窄屏、中英文、明暗主题，两个计算器的新条目搜索、选择、配图、推荐与资源汇总。离线 E2E 阻断头像网络，需额外核对新公开头像 URL；不以文字回退截图证明图片加载成功。

全部检查通过、同步清单没有未说明遗漏才报告完成。交付用简短表格列两个计算器及素材的新增／修改／删除数量、目标版本与来源，附实际测试结果。公开上游尚缺数据或图片时清楚列出阻塞范围和已完成部分；保留可工作的已核对内容，不悄悄合并不一致版本或宣称已全量同步。无需为完成本地同步自动部署或提交。
